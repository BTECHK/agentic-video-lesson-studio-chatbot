  <action>
Create chatbot/src/lib/content-retrieval.ts with:

1. A ContentContext interface:
```typescript
export interface ContentContext {
  tools: ToolData[];
  query: string;
}
```

2. A findRelevantContent(message: string): ContentContext function that:
   - Calls getAllTools() to load all 12 tools
   - Normalizes the user message to lowercase
   - Scores each tool by checking if the message contains:
     a. Tool name (case-insensitive) -- weight: 10
     b. Tool vendor name (case-insensitive) -- weight: 8
     c. Tool id (case-insensitive) -- weight: 10
     d. Any capability category key where that capability is supported -- weight: 5
     e. Words from the tool description (split on spaces, filter words > 4 chars) -- weight: 1 per word match
   - Returns tools with score > 0, sorted by score descending
   - If no tools match, return empty array (the system prompt will use bootstrap fallback)
   - Cap at top 5 tools to keep context reasonable

3. A formatContentForPrompt(tools: ToolData[]): string function that:
   - If tools is empty, return empty string
   - For each tool, format as:
     ```
     ### {tool.name} ({tool.vendor})
     {tool.description}
     URL: {tool.url}
     Priority: {tool.priority}

     Capabilities:
     - {category}: {capability.summary}
       Limitations: {joined limitations}
     ```
   - Only include capabilities where supported === true
   - Omit subFeatures, pricingTiers, versionHistory from the prompt to save tokens (the LLM can reference the tool name and the user can look up details)

IMPORTANT: content-retrieval.ts must NOT use the "server-only" import. The content.ts module uses "server-only" but content-retrieval.ts will be used from the API route (server context) so it's fine to import from content.ts there. However, for testing, content-retrieval.ts needs its own getAllTools dependency that can be mocked. Use dependency injection:

```typescript
export function findRelevantContent(
  message: string,
  toolLoader: () => ToolData[] = getAllTools
): ContentContext
```

This way tests can pass mock tool data without needing the filesystem.

Write tests FIRST (RED), then implement (GREEN). Tests should create mock ToolData objects directly rather than reading from the filesystem.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user message -> content retrieval | User-controlled text used for keyword matching |
| content JSON -> system prompt | File-system content injected into LLM system prompt |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Injection | content-retrieval.ts | accept | User message is only used for case-insensitive .includes() matching against known tool names/categories -- no regex construction from user input, no shell execution. The message goes to Claude anyway. |
| T-07-02 | Information Disclosure | system-prompt.ts | accept | Content injected into system prompt is curated course material intended to be shared with users -- no secrets in tool JSON files. |
| T-07-03 | Denial of Service | content-retrieval.ts | mitigate | Cap results at top 5 tools to prevent unbounded prompt size. formatContentForPrompt only includes supported capabilities to limit token count. |
</threat_model>
